01 / AI & FULL STACK

Synapse Solution

I engineered a real-time agentic AI dashboard that connects Finance, Sales, and Operations in one interface.

Stack: Next.js 14 · React 18 · TypeScript · Tailwind CSS · Recharts · WebSockets/SSE · Zustand

View GitHub Repository↗
Technical Walkthrough+
01

Goal / Background

I wanted to solve a common problem: Finance, Sales, and Operations teams were working from disconnected tools, which made it harder to share updates and make timely decisions. For the IBM × UTD case competition, I built Synapse Solution as one AI-assisted workspace for cross-department collaboration.

02

Implementation

I designed and shipped the dashboard with Next.js 14, React 18, TypeScript, and Tailwind CSS. I implemented real-time alerts with WebSockets and server-sent events (SSE), used Zustand for shared application state, and built interactive scenario-planning visualizations with Recharts. Users could change assumptions and immediately see the effects across departments.

03

My Role

I was the engineer responsible for building the application, including its frontend, state management, real-time alert functionality, and scenario-planning interface. Hajar Abdulkadir was our project manager, coordinating the project and keeping our work aligned with the case competition goals.

04

Impact / Numbers

The dashboard brought workflows together for 14 users. In my project results, priority-based alert routing reduced decision latency by 10%, and the scenario-planning module reduced manual planning work for three executive teams.

05

Tradeoffs / Alternatives

I used WebSockets/SSE because the dashboard needed timely updates rather than relying only on periodic refreshes. Zustand helped keep shared state manageable without adding unnecessary complexity. The tradeoff was having to handle event delivery and state synchronization carefully.

06

Optimizations

I would strengthen role-based permissions, add more automated tests for live events and cross-department scenarios, and instrument the dashboard to measure latency and alert reliability over time.

02 / DATA PLATFORM

DemandSync

I built a forecasting and ETL platform that turns transaction data into inventory decisions.

Stack: Python · Flask · PostgreSQL · REST APIs · dbt · ETL · pytest · XGBoost

View GitHub Repository↗
Technical Walkthrough+
01

Goal / Background

I wanted to help supply-chain teams make better inventory decisions using actual transaction patterns instead of relying only on manual estimates. DemandSync was my answer: a data platform that brings together ingestion, data quality, forecasting, and reporting.

02

Implementation

I architected a Flask and PostgreSQL platform to process more than 150,000 transactions through ETL pipelines. I exposed eight documented REST API endpoints, created dbt transformation layers, and wrote more than 25 automated pytest checks. I also engineered forecasting features and applied XGBoost to predict product demand.

03

My Role

I led the technical work on the data platform, including the backend architecture, transactional data processing, transformation and validation logic, REST endpoints, and forecasting workflow. I worked with the team to connect these components to the overall application.

04

Impact / Numbers

Across the project, I processed 150,000+ transactions, reduced data-retrieval latency by 10%, and achieved 99.8% pipeline reliability. The validation checks caught 12% of data anomalies before downstream processing. My XGBoost model reached 5.2% mean absolute percentage error (MAPE) across three SKUs, and the project reported a 9% reduction in overstock.

05

Tradeoffs / Alternatives

I chose PostgreSQL for structured transactional data and Flask for a straightforward Python backend. dbt and pytest gave me repeatable transformations and quality checks. XGBoost was useful for feature-based forecasting, but the model still depends on the quality and representativeness of its training data.

06

Optimizations

I would add forecast-drift monitoring, scheduled retraining, stronger API performance tests, and integrations with live inventory and procurement systems so the platform could move beyond its current project environment.

Financial Disclosure Data Pipeline

Stack: Python · SQL · ETL · APIs · SEC 10-K filings · Data validation

01

Goal / Background

I wanted to make annual financial disclosures easier to analyze. SEC 10-K filings contain valuable information, but their formats vary, so manually gathering consistent earnings metrics is slow and error-prone.

02

Implementation

I engineered a Python pipeline to crawl, ingest, clean, and structure more than 800 SEC 10-K filings. I used ETL and SQL workflows to organize 50+ financial metrics, then added 30+ automated schema and data-quality checks to validate the extracted records before analysis.

03

My Role

I designed and built the filing-ingestion, transformation, and validation pipeline. My focus was turning inconsistent source documents into dependable, structured data that could support quantitative financial analysis.

Impact / Numbers

04 / MACHINE LEARNING & FINANCIAL DATA

Oil Geo Signal Engine

I built a machine-learning research platform to study how oil prices, geopolitical news, and macroeconomic signals relate to S&P 500 movements.

Stack: Python · XGBoost · Random Forest · Scikit-learn · Pandas · NumPy · yfinance · Llama 3.3 70B · Streamlit · Plotly

View GitHub Repository↗
Technical Walkthrough+
01

Goal / Background

I set out to investigate whether oil-market changes and geopolitical events could provide useful context for interpreting broad equity-market movements, rather than analyzing prices in isolation.

02

Implementation

I assembled roughly 20 years of historical market data, including SPY, WTI and Brent crude, gold, and VIX, and engineered more than 90 features across momentum, volatility, rates, currency strength, and geopolitical risk. I added an Llama 3.3 70B-powered news-scoring agent and blended XGBoost and Random Forest models (58/42) with a 66% confidence threshold.

03

My Role

I built the data preparation, feature engineering, model research, AI-assisted news analysis, and two Streamlit/Plotly dashboards: GeoOil Intel for historical geopolitical context and Monday Alpha for model predictions.

04

Scale / Findings

The research used approximately 100,000 raw daily records, 890 Monday observations, and more than 90 signals. In my published project summary, I reported 69% accuracy on high-confidence observations; that figure describes the project's reported evaluation, not guaranteed future performance.

05

Tradeoffs / Limitations

Historical relationships can shift when market regimes change, and news-scoring models can introduce noisy or retrospective signals. A confidence threshold also reduces coverage, so accuracy must be interpreted alongside sample size and out-of-sample validation.

06

Next Steps

I would extend walk-forward validation, monitor feature drift, and make model confidence and data provenance easier to inspect in the dashboards.

06 / CIVIC TECH & MOBILITY

Autodesk SWE Case Study – LA Olympics

My team developed LA Connect during an Autodesk mock case study for LA28: a sustainable mobility concept combining rail, feeder buses, real-time travel information, and one trip-planning and payment app.

Concept: Multimodal routing · Transit & traffic APIs · Bus priority · Integrated payments · Rider incentives · Accessibility

View LA Connect App↗Network Simulation↗
Technical Walkthrough+
01

Goal / Background

During an Autodesk mock case study connected to the LA28 Olympic and Paralympic Games, our team proposed LA Connect: a sustainability-focused transportation solution intended to make Olympic travel easier, faster and more accessible for spectators, residents and visitors, while supporting local businesses.

02

Implementation

We designed a hybrid model based on LA's existing rail network, with a proposed connection to Downtown Los Angeles and feeder buses bringing nearby neighborhoods to rail stations. The app concept combines multimodal trip planning, transit payment and local food rewards. We proposed live information inputs from transit, traffic, permit and event APIs to help people plan around disruptions and event demand.

03

My Role

I helped develop and present the LA Connect concept with teammates Ramzi Burhan, Laysha Araiza, Ricardo Guardado and Enoch Omotayo. I also raised researched, thought-provoking questions during the event. The published description presents the work as a shared team proposal rather than attributing individual engineering components.

04

Impact / Proposed Service

We proposed rail arrivals every 5–10 minutes during peak periods and every 20 minutes off-peak, alongside dedicated bus-only lanes during commute hours to protect reliability. The concept aims to reduce car dependency, potentially ease pressure on the 405 and 105, expand access to transit and support foot traffic near stations. These are design targets and potential benefits, not measured outcomes.

05

Tradeoffs / Alternatives

A rail-only network can move large numbers of passengers but may not serve neighborhoods far from stations. A bus-only approach has wider reach but is more exposed to traffic. We proposed rail for high-capacity corridors, feeder buses for local access and bus-only lanes at busy times. The model would require coordination on right-of-way, service capacity, accessibility, cost and data integration before real deployment.

06

Optimizations

Next steps would include validating travel times and transfer accessibility, simulating Olympic-period demand, assessing dedicated-lane feasibility and service frequency, testing API freshness and fallback behavior, and studying whether rider incentives improve transit adoption and local-business visits.

BCOM 3300 / TEAMWORK & PROFESSIONAL WRITING

Business Communication Assignment.

Three classroom projects covering team presentations, professional writing feedback, and data-driven analysis.

01 / TEAM PRESENTATIONPresentation · My section: Voice

Sullivan, Chapters 4-5 - Team 2

Our team presented material from Sullivan Chapters 4-5. My assigned section was Voice: how vocal delivery shapes clarity, confidence, and the way an executive audience receives a message.

Six vocal delivery skills · Slide 11 Voice in executive communication · Slide 12 Nike example: weak delivery · Slide 13 Nike example: stronger delivery · Slide 14
What I covered
I explained six elements of vocal delivery: pace, volume, tone, inflection, word choice, and enunciation. Together, they help listeners follow information and interpret a speaker’s confidence, interest, and intent.
How I presented it
I defined each skill, explained how it affects executive communication, and used a hypothetical Nike boardroom scenario to compare weak delivery with a clearer recommendation about a proposed $25 million digital fitness and loyalty platform.
Why it mattered
Even a promising business idea can be difficult to evaluate when the speaker rushes, uses filler words, sounds uncertain, or presents vague reasoning. A deliberate pace, precise language, and clear emphasis help executives follow the recommendation and its next steps.
What I learned
Effective delivery is more than speaking loudly. Pausing after key figures, projecting clearly, choosing direct wording, and carefully pronouncing financial terms can make a recommendation easier to understand and discuss. The Nike example showed how the same proposal can become more persuasive when its delivery and reasoning improve.

03 / SEMESTER CAPSTONEData collection · Storage · Analysis

The Cost of Convenience - Data Analysis Capstone

For my semester capstone, I organized published grocery and energy data in Excel to explore whether changes in gasoline and crude-oil prices tracked changes in the cost of everyday staples.

Research question and hypothesis
I tested whether a basic basket of eggs, whole milk, and bananas had a positive relationship with gasoline prices. I also examined how Texas gasoline prices moved with WTI and Brent crude oil over an approximately 200-day window.
How I stored and analyzed the data
I used separate worksheets for monthly grocery prices, daily oil observations, weekly Texas gasoline prices, spike tracking, summary statistics, correlations, and a final verdict. Data sources and coverage notes are recorded in the workbook. The analysis uses formulas for correlations, variation, and statistical comparisons.
What the workbook showed
The six matched monthly observations produced a grocery-basket-versus-gasoline correlation of about -0.88, opposite the proposed positive relationship. Across 28 weekly observations, Texas regular gasoline and WTI crude oil had a positive correlation of about +0.81. These are associations in the available data, not proof of causation.
What I learned
Data storage and consistent time intervals matter as much as the chart itself. Daily, weekly, and monthly series need careful alignment; correlations are sensitive to sample size and can change by period. I learned to distinguish statistical findings from conclusions the data cannot support.

Method note: The grocery basket uses published U.S. average prices, not verified historical shelf prices from Walmart, Target, Costco, or Whole Foods. Only six monthly basket observations were available in the workbook; conclusions should be treated as exploratory.
