01 / AI & FULL STACK

Synapse Solution

I engineered a real-time agentic AI dashboard that connects Finance, Sales, and Operations in one interface.

Stack: Next.js 14 · React 18 · TypeScript · Tailwind CSS · Recharts · WebSockets/SSE · Zustand

View GitHub Repository↗
Technical Walkthrough+
01

Goal / Background

I wanted to solve a common problem: Finance, Sales, and Operations teams were working from disconnected tools, which made it harder to share updates and make timely decisions. For the IBM × UTD case competition, I built Synapse Solution as one AI-assisted workspace for cross-department collaboration.

02

Implementation

I designed and shipped the dashboard with Next.js 14, React 18, TypeScript, and Tailwind CSS. I implemented real-time alerts with WebSockets and server-sent events (SSE), used Zustand for shared application state, and built interactive scenario-planning visualizations with Recharts. Users could change assumptions and immediately see the effects across departments.

03

My Role

I was the engineer responsible for building the application, including its frontend, state management, real-time alert functionality, and scenario-planning interface. Hajar Abdulkadir was our project manager, coordinating the project and keeping our work aligned with the case competition goals.

04

Impact / Numbers

The dashboard brought workflows together for 14 users. In my project results, priority-based alert routing reduced decision latency by 10%, and the scenario-planning module reduced manual planning work for three executive teams.

05

Tradeoffs / Alternatives

I used WebSockets/SSE because the dashboard needed timely updates rather than relying only on periodic refreshes. Zustand helped keep shared state manageable without adding unnecessary complexity. The tradeoff was having to handle event delivery and state synchronization carefully.

06

Optimizations

I would strengthen role-based permissions, add more automated tests for live events and cross-department scenarios, and instrument the dashboard to measure latency and alert reliability over time.

02 / DATA PLATFORM

DemandSync

I built a forecasting and ETL platform that turns transaction data into inventory decisions.

Stack: Python · Flask · PostgreSQL · REST APIs · dbt · ETL · pytest · XGBoost

View GitHub Repository↗
Technical Walkthrough+
01

Goal / Background

I wanted to help supply-chain teams make better inventory decisions using actual transaction patterns instead of relying only on manual estimates. DemandSync was my answer: a data platform that brings together ingestion, data quality, forecasting, and reporting.

02

Implementation

I architected a Flask and PostgreSQL platform to process more than 150,000 transactions through ETL pipelines. I exposed eight documented REST API endpoints, created dbt transformation layers, and wrote more than 25 automated pytest checks. I also engineered forecasting features and applied XGBoost to predict product demand.

03

My Role

I led the technical work on the data platform, including the backend architecture, transactional data processing, transformation and validation logic, REST endpoints, and forecasting workflow. I worked with the team to connect these components to the overall application.

04

Impact / Numbers

Across the project, I processed 150,000+ transactions, reduced data-retrieval latency by 10%, and achieved 99.8% pipeline reliability. The validation checks caught 12% of data anomalies before downstream processing. My XGBoost model reached 5.2% mean absolute percentage error (MAPE) across three SKUs, and the project reported a 9% reduction in overstock.

05

Tradeoffs / Alternatives

I chose PostgreSQL for structured transactional data and Flask for a straightforward Python backend. dbt and pytest gave me repeatable transformations and quality checks. XGBoost was useful for feature-based forecasting, but the model still depends on the quality and representativeness of its training data.

06

Optimizations

I would add forecast-drift monitoring, scheduled retraining, stronger API performance tests, and integrations with live inventory and procurement systems so the platform could move beyond its current project environment.

Python pipeline that turns SEC 10-K filings into validated, analysis-ready metrics.

03 / FINANCIAL DATA

Financial Disclosure Data Pipeline

I engineered a Python data pipeline that structures SEC filings into validated, analysis-ready financial metrics.

Stack: Python · SQL · ETL · APIs · SEC 10-K filings · Data validation

GitHub Profile↗Standalone Repository Not Published
Technical Walkthrough+
01

Goal / Background

I wanted to make annual financial disclosures easier to analyze. SEC 10-K filings contain valuable information, but their formats vary, so manually gathering consistent earnings metrics is slow and error-prone.

02

Implementation

I engineered a Python pipeline to crawl, ingest, clean, and structure more than 800 SEC 10-K filings. I used ETL and SQL workflows to organize 50+ financial metrics, then added 30+ automated schema and data-quality checks to validate the extracted records before analysis.

03

My Role

I designed and built the filing-ingestion, transformation, and validation pipeline. My focus was turning inconsistent source documents into dependable, structured data that could support quantitative financial analysis.

04

Impact / Numbers

The pipeline handled 800+ filings and more than 500,000 data points. It supported analysis of 50+ earnings metrics and helped surface three earnings trends, including 4% shifts in revenue growth. My quality checks identified 6% malformed records and prevented those records from contaminating downstream analysis.

05

Tradeoffs / Alternatives

I favored automated extraction and validation rather than manual spreadsheet processing because the dataset was too large to review consistently by hand. The main tradeoff was that irregular filing layouts and changing disclosure formats could still require additional parsing rules.

06

Optimizations

I would add incremental filing updates, stronger exception handling for unusual disclosures, data-lineage tracking, and confidence indicators so analysts can trace each metric back to its original filing.

Machine-learning research into oil prices, geopolitical news, and S&P 500 movements.

04 / MACHINE LEARNING & FINANCIAL DATA

Oil Geo Signal Engine

I built a machine-learning research platform to study how oil prices, geopolitical news, and macroeconomic signals relate to S&P 500 movements.

Stack: Python · XGBoost · Random Forest · Scikit-learn · Pandas · NumPy · yfinance · Llama 3.3 70B · Streamlit · Plotly

View GitHub Repository↗
Technical Walkthrough+
01

Goal / Background

I set out to investigate whether oil-market changes and geopolitical events could provide useful context for interpreting broad equity-market movements, rather than analyzing prices in isolation.

02

Implementation

I assembled roughly 20 years of historical market data, including SPY, WTI and Brent crude, gold, and VIX, and engineered more than 90 features across momentum, volatility, rates, currency strength, and geopolitical risk. I added an Llama 3.3 70B-powered news-scoring agent and blended XGBoost and Random Forest models (58/42) with a 66% confidence threshold.

03

My Role

I built the data preparation, feature engineering, model research, AI-assisted news analysis, and two Streamlit/Plotly dashboards: GeoOil Intel for historical geopolitical context and Monday Alpha for model predictions.

04

Scale / Findings

The research used approximately 100,000 raw daily records, 890 Monday observations, and more than 90 signals. In my published project summary, I reported 69% accuracy on high-confidence observations; that figure describes the project's reported evaluation, not guaranteed future performance.

05

Tradeoffs / Limitations

Historical relationships can shift when market regimes change, and news-scoring models can introduce noisy or retrospective signals. A confidence threshold also reduces coverage, so accuracy must be interpreted alongside sample size and out-of-sample validation.

06

Next Steps

I would extend walk-forward validation, monitor feature drift, and make model confidence and data provenance easier to inspect in the dashboards.
